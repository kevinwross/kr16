# KR16 C compiler optimization plan

- Status: active
- Last updated: 2026-10-28
- Scope: `kr16 cc` code generation
- Related: [implementation.md](../implementation.md), [ADR 0003](decisions/0003-branch-relaxation.md)

## Goal

Reduce the instruction and stack traffic generated by `kr16 cc` while keeping
the compiler a teaching tool: readable code, preserved C semantics, useful
debug line information, and an `-O0` fallback.

The current backend is an AST-to-assembly emitter with `R0` as the accumulator.
Common expressions spill both operands through the stack:

```asm
LD   R0, [R4-2]
PUSH R0
MOV  R0, #1
MOV  R1, R0
POP  R0
ADD  R0, R1
```

The first two milestones target this directly.

## Baseline and targets

Measurements to record before and after each milestone:

- VM instruction count and cycles: `kr16 vm --stats image.kex`
- image text/data/bss: `kr16 size image.kex`
- generated assembly instruction count
- compile time
- behavior: output and exit code must match the `-O0` build

Corpus:

- `tests/kevin/smalltest.c`
- `tests/integration/heap.c` and `tests/support/heap_stress.s`
- `tests/unit/test_compiler.cpp` programs
- the UI demo program
- a loop-heavy test with nested arithmetic

Targets for the first pass:

- remove stack traffic from simple binary expressions (`a + b`, `a == b`,
  `a[i]`)
- fold literal-only expressions
- preserve exact C behavior and debug line mapping
- no new optimization at `-O0` until `-O1` is established

- [x] Apply safe algebraic identities where they do not drop side effects.
- [x] Keep `0 / 0`, `% 0`, and similarly exceptional cases evaluated at runtime.

Test plan:

- [x] Literal arithmetic, comparisons, shifts and unary operators produce the
  same result as the unoptimized compiler.
- [x] `if (0)`/`while (0)` bodies are not executed, including side effects in
  the skipped body.
- [x] Division/modulo by zero still diagnoses or fails as before.
- [x] Existing compiler and VM tests pass unchanged.

Notes:

- Folding operates on `Expr::Kind::Number` and `Sizeof`; no assumptions are
  made about pointer values.
- Short-circuit `&&`/`||` with literal operands folds only when the result is
  unambiguous; otherwise the branch-preserving form is kept.

### Optimization results — 2026-10-28

Benchmark source: a `while (i < 1000)` loop with `s = s + i; i = i + 1;`
compiled and linked on Windows x64. `-O0` is the straight emitter; `-O1` is
the default with M1/M2 plus the scalar IR backend.

| Build | text bytes | instructions | cycles |
|---|---:|---:|---:|
| `-O0` | 122 | 35,033 | 56,055 |
| `-O1` (M1/M2) | 74 | 16,025 | 25,041 |
| `-O1` (M3/M4 scalar IR) | 66 | 15,023 | 18,036 |

Observed reduction versus `-O0`: **57% fewer instructions**, **68% fewer
cycles**, and **46% smaller text** on that loop. These are a first data point,
not a guarantee across all programs.

Reproduce the comparison with:

```text
kr16 cc -O0 -o bench_O0.o bench.c
kr16 cc -O1 -o bench_O1.o bench.c
kr16 ld bench_O0.o -o bench_O0.kex
kr16 ld bench_O1.o -o bench_O1.kex
kr16 vm --stats bench_O0.kex
kr16 vm --stats bench_O1.kex
```

Example optimized expression:

```asm
LD   R0, [R4-2]
LD   R1, [R4-4]
ADD  R0, R1
ST   [R4-6], R0
```

Instead of the old push/pop/`MOV R1,R0` sequence.

Current M2 limits (used as the fallback outside the scalar IR subset):

- simple trees only; nested arithmetic still uses the fallback
- `a[i]`, `&x`, `*p`, calls, `&&`/`||`, and assignments through aggregates use
  the old path
- comparison results still materialize 0/1 before a following `if`; a later
  pass can branch directly on the flags

## Optimization levels

- `-O0` — straightforward emitter; best for stepping and teaching.
- `-O1` — default: M1/M2 plus the scalar IR/graph-coloring backend where
  supported.
- `-g` keeps the M1/M2 backend so local-variable debug records stay valid.
- Keep the same C semantics and diagnostics at every level.

## Notes and decisions

### 2026-10-28 — scalar IR and graph coloring

- The first IR backend deliberately targets scalar, call-free functions. This
  covers loops, arithmetic, `if`, `for`, `while`, `do`, `break`, and `continue`
  without changing aggregate/pointer ABI behavior.
- Unsupported functions and graphs that need more than five registers fall back
  to the M1/M2 emitter. That is a correctness-preserving spill policy for now;
  real stack spilling and full move coalescing are follow-up work.
- Debug builds keep the existing backend so `DebugVar` frame offsets and line
  mapping remain valid. `-O1` without `-g` uses the IR backend.
- `R4` is saved and restored around IR functions and can be colored because IR
  functions make no calls and have no stack arguments.

### 2026-10-28 — initial plan

- Peephole optimization is useful but cannot remove the core stack pattern
  without understanding the expression tree. M1/M2 therefore come before a
  textual peephole pass.
- Graph coloring is deferred until an IR with liveness exists. With only five
  allocatable registers, expression-tree allocation (Sethi–Ullman) and local
  linear scan have a better complexity/benefit ratio.
- `R0` remains the ABI result register; the first implementation only needs
  temporary pairs (`R0`/`R1`) for simple expressions.
- Branch relaxation (ADR 0003) means extra instructions from an optimization
  are safe even when a function crosses the old 256-byte branch range.
